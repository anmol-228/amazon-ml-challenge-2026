# Methodology

## 1. Problem formulation

Business entity resolution: given a primary table of business records (Source 1) and two
target tables (Source 2, Source 3), predict, for every Source-1 entity, the set of
Source-2/Source-3 records that refer to the same real-world business. Records include a
business name, address, and country; countries in training are the United States and
India, while the test set additionally includes France, with zero training examples for
that country (an explicit open-set generalization requirement). The task is scored as a
macro-average, per Source-1 entity, of F0.5 (precision weighted 2x over recall);
singleton entities (no true match) are included in the average and are scored 1.0 only if
predicted with an empty match set.

## 2. Validation design

A single frozen entity-level split (`validation_v1`, seed 42, stratified by country,
singleton status, and match-count bucket) separates a `development` partition, used for
all iteration, from an untouched `validation` partition reserved for a single confirmatory
read late in the project. Inside `development`, a second three-way split
(`matcher_train` / `dev_eval` / `calibration_holdout`, 70/15/15, same stratification and
seed) separates matcher training data from an evaluation set and a calibration set used
only for threshold/decoder selection — never for choosing model architecture or features.
The official scoring function is implemented directly from the competition's worked
example and verified against it plus 16 additional hand-constructed cases before any
model development began.

## 3. Normalization

Text is normalized with NFKC decomposition, casefolding, and whitespace collapse; Latin
diacritics are removed. Business names in non-Latin scripts are mapped to Latin tokens via
an alias map learned exclusively from `matcher_train` ground-truth links (positional token
alignment, minimum support 2, minimum share 0.6) — never from a hand-authored dictionary
and never from unlabeled data, so it introduces no country-specific hard-coding and no
external lookup.

## 4. Candidate generation (retrieval)

Candidates are generated by a hashed combination-key retrieval scheme: for each record,
keys are built from name tokens and token pairs, address tokens and pairs, normalized
address numbers, and cross terms between numbers and text tokens. Document frequency is
computed per observed-country partition over the unlabeled records being resolved (never
using labels); keys with a document frequency above a tuned threshold, or present on only
one side of the match, are dropped. TF-IDF-weighted cosine similarity then selects the
top-k targets per Source-1 record and the top-r Source-1 owners per target, unioned
together. This replaced an earlier, more expensive token/character-n-gram blocking-union
architecture (see `docs/PHASE_2_BLOCKING_REPORT.md` for that architecture's full
measurement — it establishes the project's blocking methodology but was not the retrieval
used for the final submission).

## 5. Pairwise features

Fifty-one features per candidate pair cover fuzzy name/address similarity, token and
number-set overlap, IDF-weighted overlap and unmatched IDF mass, numeric conflicts,
length and missing-field indicators, script indicators, and retrieval rank/score. IDF is
computed within each country partition of the run being resolved, with a bounded ratio, so
that feature scale does not depend on absolute corpus size — a property specifically
intended to help transfer to the unseen France partition.

## 6. Stage-1 matcher

A LightGBM binary classifier trained on `matcher_train` only, with all true positives and
a mixture of retrieval-hard and randomly sampled negatives, entity-grouped early stopping,
and a training-time augmentation that randomly rescales a subset of IDF-derived features to
reduce the model's sensitivity to corpus-specific IDF scale.

## 7. Stage-2 (collective / entity-level reasoning)

A second LightGBM classifier consumes cross-fitted stage-1 probabilities (2-fold,
entity-level, to avoid any row seeing its own stage-1 prediction as a training feature)
plus features describing the *entity-level* competition among a Source-1 record's
candidates: how many other confident candidates exist for the same entity from the same
or a different target source, the best competing probability, and this candidate's share
of the entity's and the target's total probability mass. This captures information a
purely pairwise model cannot see — for example, whether a candidate is competing against
another very strong candidate for the same entity.

## 8. Calibration and decision rule

Thresholds are selected purely on `calibration_holdout` (never on `dev_eval` or
`validation`) by exact coordinate-ascent search over the true macro-F0.5 objective. The
final decision rule conditions the acceptance threshold on two label-free properties
available at inference time: the target's source table, and the number of the entity's
candidates that are already confidently predicted. This adaptive rule is applied only to
countries observed during training; unseen countries fall back to a single global
threshold, since the adaptive rule's benefit was validated only on labeled data.

## 9. Open-set robustness

France, entirely absent from training, is handled by construction rather than special
casing: normalization and the alias map are trained-data-derived and language-agnostic,
retrieval statistics are computed per observed country of the run being resolved, and the
final decision rule explicitly limits itself to countries it was validated on. No
country-specific hand-tuned rule was adopted at any stage (see `docs/EXPERIMENTS.md` for a
rejected hand-authored France abbreviation dictionary and why it was not adopted).

## 10. Final inference pipeline

Retrieval → feature computation → stage-1 scoring → stage-2 scoring → adaptive-threshold
decoder → `matching_results.tsv` / `candidate_pairs.tsv`, validated against the official
submission format checker. Exact commands, parameters, and file hashes for every stage are
in [`student_resource/code/business_entity_resolution/README.md`](../student_resource/code/business_entity_resolution/README.md)
and [`REPRODUCIBILITY.md`](REPRODUCIBILITY.md).
